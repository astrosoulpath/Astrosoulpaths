# Fresh production Prisma migration kit — separate approval required

This directory contains six fresh-install migrations, not the historical migration chain. It must never target an existing customer/staging database. No credentials, accounts, wallets, financial orders or paid entitlements are imported. Paid product catalogue rows are initially inactive. The fourth migration adds wallet reservation/refund guards; the fifth and sixth reuse the unchanged historical moderation-correction and subscription-expiry SQL. Existing historical migration files and the first four fresh migrations remain unchanged.

Before any future approved application: verify the exact new production DB identity, PostgreSQL18, private connection/TLS, runtime isolation and approved costs. Confirm no public application tables and no application records. Pin `fresh-prisma-release-manifest.review.json` and schema hashes. Preserve the existing histories unchanged; never resolve or replay old failed migrations to use this kit.

The first migration is transactional and refuses any pre-existing public application table (Prisma's own migration history table is permitted). The second adds the reviewed SQL protections; the third validates minimal FREE/roles/languages and inactive paid catalogues and refuses existing users/wallets/payments/subscriptions. No Admin identity or allowlist is seeded. Roles are definitions, not account grants.

After separate target-specific approval, run the existing pinned Prisma6 CLI from backend-main with the approved fresh target's private DATABASE_URL/DIRECT_URL supplied only to that child process:

`pnpm prisma migrate deploy --schema ../review/payments/fresh-production-prisma/schema.prisma`

This explicitly selects only this fresh-install directory. It is NOT a preDeploy/start command and must not be replaced with a blanket migration command. Do not execute from an inherited local/staging environment. Verify all six history checksums and catalogs afterward, generate the application client from backend-main/prisma/schema.prisma, apply separately reviewed least-privilege runtime grants and verify health with payment/sending gates OFF. The product-refund schema/execution/policy gates stay OFF until separate approval and schema verification.

Phase2 evidence: all six migrations applied through Prisma6 to a new loopback-only PostgreSQL18 tmpfs container, with zero users/wallets/payments/ledger/subscriptions. A second deployment was a no-op; the resulting database had no Prisma datamodel drift. Fifteen checks covered migration history, constraints/indexes, restricted reminder-role permissions, transaction rollback and private dump/restore. The owned container was removed. No existing database was contacted. These are isolated rehearsal results, not approval to run against Render. Complete backend runtime grants, the actual hosted target identity/TLS and hosted backup/PITR remain target-specific approval requirements. Recovery uses verified backups/forward fixes, not financial-row rollback or importing expired staging data.
